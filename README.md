# Pong on Zybo Z7 (HDMI, fabric-only)

A Vivado project that implements Pong rendered over HDMI, running entirely in
programmable-logic fabric — no PS, no software, no soft-core CPU. Target board is a
[Digilent Zybo Z7](https://digilent.com/reference/programmable-logic/zybo-z7/start)
(Zynq-7020, `xc7z020clg400-1`). Output is 1280x720@60Hz (CEA-861 Format 4) via TMDS.

The design draws paddles, ball, and a playfield border over an HDMI raster, with ball
physics, collision, scoring, and a win-state FSM running at frame rate. Paddles are
pushbutton-controlled today; mouse/UART input and an AI opponent are planned additions.
The border currently renders as a closed rectangle (no goal-line opening yet), so a
scored point is a physics/score event that resets the ball to center rather than a
visible exit through the wall — opening up the border art is next on the render side.

Built with Vivado 2025.2 — confirm that matches your installed version before opening
`pong.xpr`.

## Controls

| Button | Pin | Function |
|---|---|---|
| BTN0 | K18 | Left paddle up |
| BTN1 | P16 | Left paddle down |
| BTN2 | K19 | Right paddle up |
| BTN3 | Y16 | Right paddle down |
| SW0 (`rst`) | G15 | Reset (moved from a pushbutton to a switch since all 4 buttons are needed for paddle control) |

Holding both up/down for one paddle at once cancels out rather than picking a
direction.

## Architecture

Everything runs off a single pixel clock domain (`pixclk`, 74.25 MHz) plus a 5x
serialization clock (`sysclk`, 371.25 MHz), both generated by `clk_wiz_0` from a
125 MHz input.

```
videoGen ──beam_x/beam_y/hsync/vsync/blank/frame_tick──┬──► gameRenderer ──r/g/b──► tmds_encoder (x3) ──► serializer_10to1 (x3) ──► obuffer ──► TMDS data lanes
                                                        │                                                        ▲
button_debounce ──btn_debounced──► gameLogic ──ball/paddle/score/state──┘                     tmds_constant ──► serializer_10to1 ──► obuffer ──► TMDS clock lane
                         ▲
                    pong_pkg (shared playfield/paddle/ball geometry)
```

1. **`videoGen`** (`imports/rtl/videogen.sv`) — free-running H/V counters; the sole
   source of raster timing and blanking. Emits one `frame_tick` per frame.
2. **`button_debounce`** — synchronizes + debounces the 4 raw pushbutton inputs into
   the `pixclk` domain.
3. **`gameLogic`** — the game itself: ball physics, paddle position, scoring, and a
   4-state FSM (`ST_PLAY` / `ST_GOAL_L` / `ST_GOAL_R` / `ST_GAME_OVER`, first to 7
   points wins), advanced once per `frame_tick` (60 fps), independent of pixel timing.
4. **`pong_pkg`** — shared playfield/paddle/ball geometry (field bounds, paddle size,
   ball size, centered starting positions) so `gameRenderer` and `gameLogic` can't
   drift out of sync.
5. **`gameRenderer`** / **`testPattern`** — pure combinational pixel-color generators
   driven by `beam_x`/`beam_y`/`blank`. Only `gameRenderer` is wired live in
   `toplevel.sv` right now.
6. **`tmds_encoder`** (x3) — 8b/10b TMDS encoding, one per color channel; the blue
   channel also carries `hsync`/`vsync` as `ctrl`.
7. **`serializer_10to1`** (x4: 3 color + 1 clock lane) — OSERDESE2 MASTER/SLAVE
   cascades doing 10:1 parallel-to-serial at `sysclk`.
8. **`obuffer`** (x4) — `OBUFDS` wrappers driving the differential `tmds_data_p/n` and
   `tmds_clk_p/n` top-level ports.

`clk_divider` is a standalone debug/heartbeat module (blinks `led0` off `pixclk`,
drives `led1` from MMCM `locked`) — not part of the display pipeline. `led2` lights
when `gameLogic` reaches `ST_GAME_OVER`.

## Pinout

| Signal | Pin | Notes |
|---|---|---|
| `mmcmclk` | K17 | 125 MHz board oscillator |
| `rst` | G15 | SW0, active per RTL polarity |
| `led0` / `led1` / `led2` | M14 / M15 / G14 | heartbeat / MMCM locked / game-over |
| `tmds_data_p/n[2:0]` | see XDC | HDMI data lanes |
| `tmds_clk_p/n` | H16/H17 | HDMI clock lane |
| `btn_l_up/down`, `btn_r_up/down` | K18/P16/K19/Y16 | BTN0-3 |

SW1-3 (P15/W13/T16) and LED3 (D18) are unused and free for future features.

## Repository layout

Only the following are real, hand-authored/tracked sources — everything else at the
repo root (`pong.cache/`, `pong.hw/`, `pong.ip_user_files/`, `pong.runs/`, `pong.sim/`,
`pong.gen/`) is Vivado-generated and gitignored; don't hand-edit it.

```
pong.xpr                                     Vivado project file
pong.srcs/sources_1/new/*.sv, *.v            RTL modules
pong.srcs/sources_1/imports/rtl/videogen.sv  imported RTL (raster timing)
pong.srcs/sources_1/ip/clk_wiz_0/            Clocking Wizard IP definition
pong.srcs/constrs_1/new/clk_divider.xdc      pin constraints + ILA debug-core config
pong.srcs/sim_1/new/*.sv                     testbenches
```

## Simulation

Testbenches live in `pong.srcs/sim_1/new/`:

- `gameLogic_tb.sv` — reset values, ball motion/wall bounce, paddle motion (including
  both-buttons-held cancellation), scoring, post-goal serve delay, game-over
  latching/recovery.
- `button_debounce_tb.sv` — a short glitch doesn't propagate, a sustained level change
  does, and each bit debounces independently.
- `serializer_tb.sv` — walking-1 pattern through `serializer_10to1`, checks 10:1
  serialization ordering/timing.
- `smoke_tb.sv` — currently stale/disabled (`UserDisabled` in `pong.xpr`); references a
  module that no longer matches anything in this repo.

Run via Vivado's XSim (Flow Navigator → Simulation → Run Simulation), or from the
command line with Xilinx's standalone simulator (`xvlog`/`xelab`/`xsim`, on `PATH`
under `/opt/Xilinx/2025.2/Vivado/bin`):

```sh
xvlog -sv <files in dependency order, packages first>
xelab -debug typical <top_module> -s <snapshot_name>
xsim <snapshot_name> -runall
```

A full-chip elaboration of `toplevel` needs the Xilinx primitives library and `glbl`:

```sh
xelab -debug typical toplevel glbl -s <snap> -L unisims_ver
```

(`glbl.v` is at `/opt/Xilinx/2025.2/Vivado/ids_lite/ISE/verilog/src/glbl.v`; the
`clk_wiz_0` behavioral model is generated output at
`pong.gen/sources_1/ip/clk_wiz_0/clk_wiz_0.v`, present after Vivado has generated the
project once.)

There is no Makefile, CI, or test runner — all building, simulation, and bitstream
generation happens through the Vivado GUI or Tcl console.
